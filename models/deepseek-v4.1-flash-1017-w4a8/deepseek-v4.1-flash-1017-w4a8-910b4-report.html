DeepSeek-V4.1-Flash-1017-w4a8 on Ascend 910B4: baseline against tuned

Measured 2026-11-05/06 on a production Atlas 800T A2 cluster, vLLM-Ascend 0.30.0rc2, one instance of 8 cards, driven directly over the pod network. Hand-run campaign, not an AutoTune report.

1. What the two variants are

Both run the same image, by digest: quay.io/ascend/vllm-ascend at sha256:7859b751…. The pair tunes configuration, not builds.
Baseline vllm-tp8-910b4-baseline — the vLLM cookbook's A2 example copied as it stands: 32 sequences, memory utilisation 0.90, 8192-token prefill chunk, and its own environment block and four additional-config switches.
Tuned vllm-tp8-910b4-optimized — 48 sequences, utilisation 0.95, the same 8192 chunk, those four switches off, and HCCL_BUFFSIZE=1024 with HCCL_OP_EXPANSION_MODE=AIV.

The tuned configuration is the best of a scan of some two dozen configurations on the workload described next; the baseline is that same scan's reference point, the vendor's published example. Section 4 is what the scan says about why each parameter moves the number.

2. The workload

50K input tokens, 1500 output tokens per request, a fixed pattern load held for the whole window against the engine's own HTTP endpoint. No router, no second instance, no multi-turn reuse: one engine, one client.

Each configuration runs at its own seat limit, because that limit is part of the configuration: the cookbook sets --max-num-seqs 32 and was driven at 32 concurrent requests, the tuned one sets 48 and was driven at 48. That is the question a deployment asks: what does this configuration do when it is full.

The window has to be long. This load is a sawtooth: a batch is admitted together, prefills together (input tokens high, output near zero), then decodes together. A request lives about 1459 s at 32 concurrent, so a 10-minute window sits inside one half-cycle and, measured inside a single run, reads 1.80× higher than the long one. Every figure below is the long window: 2742.1 s at 48 concurrent, 2646.1 s at 32.

2.75× the throughput, and time to first token falls from just over six minutes to under one — on a load where every request carries a 50K-token prompt, queueing is most of the latency, and the tuned configuration drains the queue faster than it fills.

4. Why the engine parameters pay

Sequence count and memory fraction are one change, not two

--max-num-seqs is only a seat limit; it does not create the memory to hold those requests. --gpu-memory-utilization does: whatever is left after weights and activations becomes the KV pool. A request of this workload (50K in, 1.5K out) holds about 51,500 tokens of KV, and the measured pools hold 36.8 such requests at 0.90 against 49.6 at 0.95 — which is what makes 48 sequences schedulable at all. The two have to move together. Raising utilisation where the seats were already enough measured −10.4% on this same hardware with another model, so this is not a “more is better” knob.

The prefill chunk has an optimum, not a direction

A bigger --max-num-batched-tokens makes prefill kernels more efficient, but its activation memory is taken out of the same KV pool: every extra 4096 costs some 600–690K tokens of pool, about 12–13 seats. Measured across the scan, 2048 → 8192 rises monotonically, 12288 falls 21.3%, and 16384 is refused at startup for want of KV. The optimum is the largest chunk whose pool still seats the target concurrency.

Four Ascend switches that cost 42%

The cookbook turns on enable_npugraph_ex, enable_dsa_cp, enable_flashcomm1 and enable_shared_expert_dp inside --additional-config. On this A2 hardware that group measured −42.3% against the same configuration without it, so the tuned variant leaves all four off. This is the one place where the baseline carries more optimisation than the tuned variant — read the pair as a diff, not as a delta.

Collective communication

HCCL_BUFFSIZE=1024 with HCCL_OP_EXPANSION_MODE=AIV, where the AI vector cores drive the transfer instead of the AI CPU scheduling it, measured +39.3% as a pair (1,861.0 → 2,592.8 at 48 concurrent). Their individual shares were never isolated, so neither should be quoted alone. A MoE model that collects across all 8 cards on every step is where that scheduling overhead lives.
